How to use this guide

Read it from the start if the words packet, MAC, and port are still fuzzy. If you already know what an IP address is, skim Part 1 and start at Part 2. Each part ends with a small exercise. The answers are at the back so you can try before you look.

The running inspector at http://127.0.0.1:8765 shows the same bytes this guide describes. Start it from the project folder with .\build\nip-view.exe when you want to check a claim against a real parse.

This guide explains ideas. It does not tell you how to attack a network. The parser only reads bytes you already have, from a sample frame or, later, from a capture file you are allowed to open.

1. Beginner: what is moving on a network

Hosts, interfaces, and addresses

A host is a machine that sends and receives data: a laptop, a phone, a server. The host reaches the network through an interface. On a wired PC that interface is an Ethernet port. On Wi-Fi it is a wireless adapter. Each interface has a hardware address, the MAC address, burned into or assigned to that adapter. A MAC address is 48 bits, usually written as six hex bytes, such as 00:0A:0B:0C:0D:0E.

An IP address is a different kind of name. It identifies a host in an IP network, not one physical adapter in the same way a MAC does. IPv4 addresses are 32 bits, written as four decimal numbers, such as 192.168.1.10. A port number is smaller still. It identifies one program on that host. Port 80 is commonly a web server. Port 53 is commonly DNS. MAC, IP, and port answer three different questions: which adapter, which machine in the IP network, and which program.

A packet is an envelope inside an envelope

People say “packet” for the whole thing that travels. More precisely, each layer adds its own header and calls the result by its own name.

An Ethernet frame is the link-layer envelope. An IPv4 packet is the network-layer envelope inside it. A TCP segment or UDP datagram is the transport-layer message inside the IP packet. The application data, such as an HTTP request, sits inside the transport message. Parsing means walking inward, one header at a time, and stopping when a length check fails or when the next protocol is one this program does not decode.

Bits, bytes, and hexadecimal

A bit is 0 or 1. A byte is 8 bits and can hold a number from 0 to 255. Hexadecimal writes a byte as two digits. One hex digit is 4 bits, called a nibble. 0x45 is the byte with high nibble 4 and low nibble 5. In the first byte of an IPv4 header those two nibbles are separate fields: version 4, and header length 5 words. That single byte is why the inspector’s first IPv4 sample starts with 45.

2. Reading bytes without lying to yourself

Network byte order

When a field is wider than one byte, the bytes have an order. Network protocols use big-endian order: the first byte on the wire is the most significant. The two bytes 08 00 are the number 0x0800 (2048), which is the EtherType for IPv4. If you swapped them you would invent EtherType 0x0008, and every later decision would be wrong.

Your CPU may be little-endian, which stores the low byte of a number at the lower address. That is an internal detail of the computer. It is not the order of bytes in a frame. ByteReader::readU16Be and readU32Be rebuild the number from the first byte as the high byte. The test ByteReader.ReadsNetworkByteOrder locks this down: {0x08, 0x00} must become 0x0800, and the next four bytes C0 A8 01 0A are the 32-bit value of 192.168.1.10.

Never overlay a struct on the buffer

A tempting shortcut is a packed C struct and a cast of the packet pointer. That is a bad parser. The compiler may insert padding between fields. The CPU endianness may not match the wire. A short frame would let the cast read memory past the buffer. NIP copies fields out with checked reads. A read that would pass the end returns no value and leaves the cursor where it was. The frame is not “mostly fine.” It is malformed.

Three honest outcomes

StatusMeaningExample in the inspector
successThe header was long enough and its length fields were legal.IPv4 TCP header
unsupportedThe protocol was recognized and this milestone does not decode it. The bytes were not treated as valid IPv4.IPv6 EtherType, ARP
malformedA length or structure check failed. The header is not reported as valid.Truncated Ethernet, invalid IHL

Unsupported and malformed are different. IPv6 is a real protocol. A 13-byte buffer is not an Ethernet header. Mixing those up hides broken captures inside a pile of “unknown” packets.

3. Ethernet, the outer envelope

This milestone parses Ethernet II frames. The header is 14 bytes and does not include a preamble or checksum. Those are usually stripped by the capture device before your program sees the frame.

012345678910111213
Destination MACSource MACEtherType

The destination is who should receive the frame on this link. FF:FF:FF:FF:FF:FF is the broadcast address: every station on the LAN. The source is the sender’s adapter. The EtherType tells you how to read the payload.

EtherTypeMeaning in NIP
0x0800IPv4. Parsing continues into the payload.
0x86DDIPv6. Recognized, not parsed. Status is unsupported.
0x0806ARP. Known, unsupported in this milestone.
0x8100VLAN tag. Unsupported until a later milestone peels the tag.
1500 or lessAn IEEE 802.3 length, not an EtherType. Unsupported.

Fewer than 14 bytes is malformed, because the three fields cannot fit. A legal 14-byte header with an empty payload is still a successful Ethernet parse. The payload view starts at byte 14 and is what the next parser receives.

4. IPv4, the network header

The fixed part of an IPv4 header is 20 bytes. It can be longer when options are present. The parser must discover that length before it touches anything after the header.

Byte 0Byte 1Bytes 2–3
VersionDSCP / ECN, skippedTotal length
Bytes 4–5 IdentificationBytes 6–7 Flags and fragment offset

Bytes 12–15 Source address
Bytes 16–19 Destination address

Version and header length

Version must be 4. Anything else is malformed for this parser, even if the bytes happen to look a bit like IPv4. The Internet Header Length (IHL) is the low nibble. It counts 32-bit words, not bytes. The byte length is IHL × 4.

First byteVersionIHLHeader bytesVerdict
0x454520Minimum legal header
0x46462420 bytes plus 4 bytes of options
0x4F41560Longest legal IPv4 header
0x444416Malformed. IHL must be at least 5
0x6565—Malformed for the IPv4 parser. Version is not 4

IHL 6 with only 20 captured bytes is also malformed. The header claimed 24 bytes and the buffer ran out. A complete header whose payload was cut off is different: the header parsed, and the missing tail is a short capture, not a broken header.

Total length, padding, and checksum

Total length is the IPv4 header plus its payload, in bytes. It must be at least the header length. Ethernet frames are padded to a minimum size, so the captured buffer can be longer than the IP packet. Bytes past the total length are padding and are not part of the IP payload. The sample “IPv4 TCP header” has total length 20, so the payload after the header is empty even if extra bytes were glued on the end.

The header checksum is stored and not verified in this milestone. A bad checksum does not, by itself, make the parse malformed yet. Extracting it still matters, because those two bytes have to be consumed so the addresses land on bytes 12 through 19.

TTL is the hop limit. Each router that forwards the packet decreases it. Protocol is the next header’s number: 1 is ICMP, 6 is TCP, 17 is UDP. Any other number is still a successful IPv4 parse. The next protocol is simply unsupported.

Options

Options occupy the bytes from offset 20 up to the header length. The walk is structural. It does not need to understand every option type.

  • 0 is the end of the option list. Later bytes in the options area are padding.
  • 1 is a no-operation, one byte long. It aligns the next option.
  • Any other type is followed by a length byte. That length includes the type and the length byte, so it must be at least 2, and the option must end before the header ends.

The “IPv4 options” sample is 01 01 01 00: three NOPs and an end. The header is 24 bytes and the Don’t Fragment flag is set. An option that says its length is 5 while only 4 option bytes exist is malformed. The parser refuses to start the transport header at a guessed offset.

5. Fragmentation

A router may split a large IPv4 datagram into fragments. They share one identification value so the receiver can group them. The flags and offset share one 16-bit field.

BitsNameMeaning
15ReservedMust be zero in normal traffic. NIP records it and does not invent a failure from it alone.
14DFDon’t Fragment. If the packet does not fit a link, it is dropped instead of split.
13MFMore Fragments follow. Clear on the last fragment and on an unfragmented packet.
12–0OffsetWhere this fragment’s payload belongs, in units of 8 bytes.

Offset 0 is the first fragment, including a packet that was never fragmented. The transport header, if any, starts there. Offset 5 means this fragment begins at byte 40 of the original payload. The bytes at the front of this fragment are the middle of a TCP stream or a UDP datagram, not a fresh TCP header. NIP records the IPv4 header as success and does not parse a transport header.

The sample uses flags-and-offset 0x2005. Bit 13 is set, so More Fragments is true, and the low 13 bits are 5. The inspector shows offset 5 and 40 bytes.

6. Advanced: TCP, UDP, and ICMP

These headers are the next parsing milestone. The models and the length rules already exist in the code. The inspector shows the IPv4 protocol number and stops. This section is the map for that next step.

TCP

TCP is a reliable byte stream between two ports. The fixed header is 20 bytes and can grow to 60 with options, the same word-count trick as IPv4. The data offset is a 4-bit field. Header length in bytes is data offset × 4. A data offset below 5, or a header that does not fit in the captured bytes, is malformed.

FieldSizeWhat it is for
Source port, destination port2 bytes eachThe programs at each end
Sequence number4 bytesWhere this segment sits in the byte stream
Acknowledgment number4 bytesThe next byte the sender expects, meaningful when ACK is set
Data offset4 bitsHeader length in 32-bit words
FlagsbitsSYN starts a connection, ACK acknowledges, FIN and RST close or abort, PSH asks for prompt delivery
Window2 bytesHow many more bytes the sender is willing to receive

TCP and UDP both have ports. TCP adds sequence numbers and flags because it reconstructs a stream and reacts to loss. Parsing one header does not reassemble that stream. It only records the fields of this segment.

UDP

UDP is a short datagram. The header is always 8 bytes: source port, destination port, length, checksum. The length includes those 8 bytes, so a length below 8 is malformed. A length larger than the bytes still available is a truncated datagram. A length smaller than the IP payload is legal. The extra bytes are not part of this UDP datagram.

UDP does not retransmit and does not order messages. DNS queries and many real-time streams use it because a late retransmission is useless. The parser’s job is still the same: do not read a port from a buffer that does not contain four bytes of ports plus four more bytes of length and checksum.

ICMP

ICMP is a control protocol carried inside IPv4, protocol number 1. It is not a transport for application data in the way TCP and UDP are. Echo request (type 8) and echo reply (type 0) are the familiar ping. Destination unreachable (type 3) and time exceeded (type 11) report delivery problems. The fixed front of the message is type, code, and checksum. A full ICMP header is 8 bytes. Shorter than that is truncated. The checksum is extracted. This milestone does not fail the packet only because the checksum arithmetic was not run.

7. Captures, truncation, and the inspector

What a PCAP file will be

A PCAP file is a recording of frames, each with a timestamp and two lengths: how many bytes were stored, and how long the frame was on the wire. A capture can be snapped short on purpose. If the stored bytes include a full IPv4 header but not the whole TCP header, the IPv4 parse can succeed and the TCP parse must be malformed. That distinction is the point of checking lengths against the buffer you actually hold, not against the length the sender wished it had sent.

The PCAP reader is not in the program yet. When it is, PcapPlusPlus will open the file and hand over raw bytes and a timestamp. It will not decode Ethernet or IP for us. The link type must be Ethernet. Another link type would be reported and left unparsed, because those bytes are not an Ethernet header. The Npcap driver is the Windows library that file reading will load. It is not installed on this machine yet, so that stage cannot run until it is.

How a click in the inspector becomes fields

  1. The page loads GET /api/samples or posts the hex you typed to POST /api/parse.
  2. decodeHex accepts spaces, colons, dashes, and a 0x prefix. An odd number of digits or a character that is not hex is rejected before any parser runs.
  3. inspectFrameJson calls parseEthernet on the whole buffer.
  4. Only a successful Ethernet parse whose EtherType is IPv4 calls parseIPv4 on the payload view. IPv6 and ARP keep the Ethernet header and set IPv4 to null.

The code that does this lives in src/parser/EthernetParser.cpp, src/parser/IPv4Parser.cpp, and src/view/Inspect.cpp. The tests in tests/EthernetParserTest.cpp and tests/IPv4ParserTest.cpp are the same lesson as the samples, written as byte arrays.

8. Practice, in order

  1. Open the IPv4 TCP sample. Write the destination MAC, source MAC, EtherType, source IP, and destination IP from the panels, then find each one in the hex pane.
  2. Change only the EtherType in the paste box from 08 00 to 86 DD and parse. The MAC addresses stay. The IPv4 panel should disappear and the Ethernet status should become unsupported.
  3. Open the options sample. Confirm the first IPv4 byte is 46 and that the header length is 24.
  4. Open the fragment sample. Compute 5 × 8 yourself before you read the “40 bytes” line.
  5. Paste a 10-byte buffer of 45 repeated. It cannot be an IPv4 header. The status should be malformed.
  6. Build 0x45 on paper from version and IHL, then 0x46, then explain why 0x44 is rejected.
  7. When you implement TCP, write a 20-byte TCP header behind a 20-byte IPv4 header and check that a data offset of 4 is rejected while 5 is accepted. Do that in a unit test with a byte array, the same way the IPv4 tests work.
